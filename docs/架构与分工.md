# 架构与分工

> 对应方案：`电商平台AI客服方案_v0.2.md`（下称「方案」）。本文件描述代码怎么组织、模块之间的契约，
> 以及并行开发时每个模块归谁。方案是"做什么"，这里是"代码里怎么落"。

## 1. 分层与依赖方向

```
rodit.core            契约层：枚举、数据模型、判断层格式（Jev）与 state 构造、端口协议、配置、
                      证据规则、共享词表、个人信息最小化、审计事件名、每种路由结果的执行计划
rodit.inmemory        core.ports 的内存实现：各仓储、缓存、离线向量（测试、本地演示、模式 C 单进程）
  ↑ 所有子包只依赖 core（+ inmemory）；子包之间不互相 import（组装在 rodit.app / 测试里做）
rodit.decision        判断层实现（§6.4）            rodit.knowledge   知识中心（§5.2）
rodit.routing         路由规则（§6.6）              rodit.tools       平台只读工具、物流（§7.1、§7.2）
rodit.generation      答案生成（§5.4）              rodit.aftersale   售后问答依据 + 审核助手（§7.3）
rodit.qa              答案质检（§5.5）              rodit.adapters    平台接入层（§8）
rodit.engine          编排：懂→找→写→判（§5）       rodit.feedback    反馈闭环与报表（§5.8、§12.4）
rodit.storage         PostgreSQL 仓储（§9.2、§10）   rodit.llm         大模型 HTTP 客户端（D5）
rodit.eval            评测与校准（§13）             rodit.api         HTTP 接口（模式 C、反馈、审核）
rodit.testing         合成数据、测试替身、仓储契约测试（contracts）；只用于测试和本地演示
```

例外：`rodit.routing` 可以依赖 `rodit.decision`（路由在判断层不可用时要退回规则实现）。
集成阶段新增的 `rodit.app`（组装）、`rodit.api`、`rodit.eval` 可以依赖所有子包。

## 2. 一条买家消息怎么走（§4.2、§11）

```
PlatformAdapter.peek_shop_id(raw) → 店铺（不改任何状态）      （app 层据此核对调用方身份和授权，§9.2、§8.4）
PlatformAdapter.on_event(raw) → StandardMessage | 回声 | 撤回  （adapters，平台差异止于此）
  → 客服 / 机器人发出的文字（回声）写进会话；撤回的消息从会话里去掉、按它给的推荐过期并刷新侧边栏，
    撤回先于消息到达时留标记，消息到了也不保存、不回答（app 层 + 会话仓储）
  → ConversationRepository.add_message（按 msg_id 去重）；晚到的旧消息只入库，重算最新一轮（§8.3）
  → 会话理解：合并连发、最近 5 轮、指代到商品 / SKU / 订单 → ConversationContext   （engine）
  → Router.route(ctx) → RouteDecision                        （routing + decision，§6.6 八条规则）
  → EvidenceRetriever.retrieve(ctx, route) → EvidenceBundle  （knowledge；工具证据经 ToolEvidenceProvider）
  → AnswerGenerator.generate(...) → [Draft]                  （generation：FAQ / 模板优先，其次大模型）
  → QualityGate.check(...) → QAResult                        （qa：硬规则 + 判断层质检，不过则带原因重写一次）
  → EngineResult（推荐卡片 / 提醒 / 转人工 / 缺失知识）       （engine）
  → PlatformAdapter.show_suggestions / send（仅全自动）       （app 层）
  → 客服操作 → FeedbackService（采纳、修改、弃用）             （feedback）
```

售后审核是另一条链路：`ToolGateway` 拉售后单 → 审核规则 R1–R8 → 状态机 → 客服确认 →
重读状态 → `AfterSaleActionPort`（幂等键）→ 审计。问答引擎永远不碰写接口。

运营闭环（Phase 1，§5.2、§9.1、§13.4、§13.5）：

```
商家控制台（AssistService.console）  FAQ / 政策 / 商品卡片商家字段 / 店铺配置 → KnowledgeRepository
                                     （配置、卡片按字段原子修改）；商品同步：ItemCatalog + ImageTextExtractor
                                     → 只改平台维护的字段
推荐记录（带路由置信度、§6.6 规则）→ 客服发送 / 编辑后发送 / 理解错误 → LabeledSample（带置信度、规则）
  → recalibrate（只用规则 6，辅助阈值只维持或上调）→ 阈值建议（人工合并进配置）
  → train-classifier → 模型文件 → RODIT_CLASSIFIER_PATH（decision.provider: classifier）
  → 上线前 python -m rodit.eval [--classifier] --baseline 回归（§13.5）
上线节奏（AssistService.rollout）  影子对比 + 每周复核（QualityReview，§13.2 打分）→ 门槛
                                  → 复核人员切到智能辅助（没过门槛要强制并写原因，审计留痕）
```

## 3. 契约约定（所有模块都要遵守）

- **标准格式**：引擎只认 `core.models.StandardMessage`；判断层只认 `core.decision` 的 Jev 格式，
  state 只由 `core.states` 构造（内部已脱敏）。
- **配置分层**：`Shop.config_overrides` 只存店铺覆盖项；生效配置用 `core.config.effective_shop_config`
  算出，放在 `ConversationContext.config`，各步骤只读它（§9.3）。
- **执行计划**：每种路由结果跑哪些步骤见 `core.pipeline.ACTION_PLANS`；多问题（规则 5）按
  `RouteDecision.parts` 分条执行。
- **留痕分工**：decision_log 由 Router（route）和 QualityGate（qa）写；audit_log 的事件名见
  `core.audit.AuditAction`，引擎每条消息写一条 `engine.result` 汇总；推荐记录由引擎写入并负责过期。
- **证据 ID 与冲突**：只能用 `core.evidence` 的构造函数；各类证据 `data` 的结构、topic 冲突规则
  （被覆盖的证据从 evidences 移除、只记 id）见该模块文档字符串。平台规则是单独的证据来源（PLATFORM）。
- **问题定义**：路由和质检的问题在 `core.questions`，改文字会改版本号（写进 decision_log）。
- **个人信息**：任何进提示词、判断层请求、审计日志的买家文本都先过 `core.pii.mask_pii`；
  模型里没有昵称、手机号、地址字段；`buyer_ref` 由注入的 `core.pii.BuyerRefHasher` 生成（盐来自
  环境变量，测试用 `fixtures.TEST_SALT`）。
- **Jev**：判断层实现有 `accepts_buyer_data`；Router / QualityGate 构造时用
  `core.decision.require_buyer_data_ok` 拒绝不能处理买家数据的实现；配置里 provider 不能是 jev（§6.2）。
- **售后写操作**：写接口只接受 `HumanConfirmation`；幂等键用 `aftersale_idempotency_key`（平台状态版本）；
  状态机合法迁移见 `REVIEW_TRANSITIONS`，可操作状态见 `ACTIONABLE_STATUSES`。
- **店铺隔离**：所有仓储方法、缓存都按 `shop_id` 分开，实现不得跨店返回数据（§9.2）；
  仓储实现都要通过 `rodit.testing.contracts`（含串店测试 `check_cross_shop_isolation`）。
- **时间**：业务代码用注入的 `Clock`，不直接调 `datetime.now()`；所有时间带时区。
- **异常**：用 `core.errors` 的类型表达可降级的失败（`LLMError`、`DecisionError`、`ToolUnavailable`…），
  降级规则见方案 §12.2。
- **只读**：问答链路只用 `ToolGateway`；`AfterSaleActionPort` 只有售后审核助手能用，且必须有人确认。
- **测试**：单元测试不依赖网络；大模型用 `testing.fakes.FakeLLMClient`，平台用 `InMemoryToolGateway`，
  数据用 `testing.fixtures.build_demo_world()`（全部合成）。PostgreSQL 测试打 `@pytest.mark.pg`，
  连不上时自动跳过。

复审之后加的契约：`ShopAuth.granted_at`（开通事件时间）/ `ShopAuth.version`（全单元不重复的写入版本，
标记需要重新授权不改它）、`GrantStamp`、`ShopAuthRepository.replace(auth, expected_version=…)`（续期按版本
条件写回，只更新、不新建）/ `stamp`（不解密读版本和开通时间）/ `mark_needs_reauth(…, expected_version=…)`、
`TokenProvider.report_rejected(shop_id, token=None)`（带上被拒的令牌时只标记它所在的那一份）、
`AssistService.revoke_shop(shop_id, guard=, on_purged=)`（判断和清理记录都在写方闸门里）、
`core.budget.BackgroundWork` / `background_scope`（`submit_in_context` 提交的线程池任务按店铺记着，取消订购先等
它们做完）、`core.config.llm_endpoint`（线上用哪个大模型的唯一规则）、`AuditAction.COMPLIANCE_REVIEWED`，
迁移版本 5 加了 `granted_at`、`version` 列和 `shop_auth_version_seq`。
第二轮复审：`AuditAction.SHOP_PURGE_STARTED`（系统事件 `shop.purge_started`：在写方闸门里、删令牌之前写的开始清理
标记，detail 只有店铺 ID、原因和 `event_at`；系统事件的读策略不按动作过滤，没有新迁移）、
`TenancyService.unfinished_purges()`（有标记、之后没有 `shop.purged`、令牌也不在的店铺；`purge_expired` 每轮先
接着删完，闸门里确认还没有授权）、`TenancyService.onboard(…, granted_at=)`（运维开通只记给出的平台开通时间，
不给时为空、不参与订购事件排序；`onboard-shop --granted-at`）。

约定：
- 引擎里所有写记录（审计、判断日志、推荐记录、缺失知识）都在调用线程上、截止时间之内做；并行的只有读和调模型。
  线程池一律经 `core.budget.submit_in_context` 提交（带上截止时间、店铺范围，在引擎里还记进 `BackgroundWork`）。
- 平台单元 Phase 1 只跑一个副本（`serve` 的咨询锁租约强制）；会话锁、取消订购闸门、抽样锁都在进程内，
  多副本之前要换成共享实现（选型记录：多实例部署时再换 Redis）。
- 改店铺数据的运维命令（`onboard-shop`、`refresh-tokens`、`purge-expired`、`revoke`、`set-status`）和 `serve`
  拿同一个租约；续期、过期清理、就绪检查、授权过期检查在 `serve` 的后台线程里按间隔跑（`rodit.ops.background`），
  `/metrics` 不查库。`compliance-scan` 不拿租约（每周跑、只追加计数）：写之前看扫描开始之后有没有开始清理这家店
  （`shop.purge_started`，按整次扫描的开始时间、放 5 分钟时钟余量），有就这次不写；写完再确认店铺还有授权，没有就删掉这次的写入，
  有但扫描期间清理过（清理完又重新开通）就提示核对、重新扫描。
- 清理中途出错或进程被杀不靠内存里的重试记录：开始清理的标记落库，`purge_expired`（`serve` 后台任务、
  `purge-expired` 命令）每轮先接着删完，重启之后也一样。
- 订购事件按平台事件时间排先后（每家店的最新事件时间 = 授权的 `granted_at` 和 `shop.purged` 的 `event_at`；
  开通 / 续订还比 `shop.purge_started` 的 `event_at`），过时的一律 `ignored`；判断在这家店的写方闸门里做。
  `granted_at` 只记平台的事件时间，不拿本机时间冒充。

### 4.4 真实大模型评测前的加固（§13、§12.1、§14）

第一次用真实的境内大模型跑 `python -m rodit.eval --llm env` 之前查出来的问题：调用失败、被截断、读不出时，
链路按 §12.2 降级，评测照样跑完、退出码是 0，报告里的数字量的却是兜底逻辑，不是模型。这一轮只修开跑前必须修的。

契约（T0，已合入）：
- 调用结果：`LLMResponse.finish_reason`（接口返回的 finish_reason，没给时为 None；`length` 表示输出被
  max_tokens 截断）。
- 失败原因：`LLMError(msg="", *, status=None, kind=None, code=None)`，`LLMTimeout` 同一套参数、`kind` 默认
  `timeout`。`status` 是 HTTP 状态码（收到了响应时）；`kind` 是 `LLMErrorKind` 里的一类（`LLM_ERROR_KINDS`：
  timeout、rate_limit、auth、billing、bad_request、content_filter、server、redirect、network、malformed、config，
  含义见 `core.errors`；不认识的取值抛 ValueError）；`code` 是模型服务给的错误代码或类型（短字符串）。三项都可以为空，
  会原样进审计、日志和评测报告：不放密钥、提示词、买家文字，`code` 也不放错误消息原文。`LLMError("…")` 这样的老写法照旧。
- 模型服务特有的请求参数：`LLMConfig.extra_body`（YAML 的 `llm.extra_body`，默认空），原样并入每次
  chat/completions 请求，常见用途是关闭思考模式（`config/rodit.yaml` 里有注释掉的例子）。特意算进
  `config_fingerprint`：这一项不一样，评测和部署发出去的请求就不一样，不能看成同一套配置；所以只从配置来，
  不另开环境变量的入口（那样给的值不在指纹里）。不放密钥（进指纹、可能被打印）；不能有 `LLM_EXTRA_BODY_RESERVED`
  里的键（客户端按每次请求自己填的：model、messages、temperature、max_tokens、stream、response_format、logprobs、
  top_logprobs），取值要能序列化成 JSON，否则加载配置时报错并点名是哪个键。现在还没有地方读它：评测（C2）和
  生产组装（A）构造客户端时传 `extra_body=config.llm.extra_body`。
- 运行健康度 `rodit.eval.health`（纯数据和纯函数，只依赖 pydantic 和标准库）——报告里 health 这一块的结构，
  和判定"这一轮算不算评到了模型"的唯一一条规则：
  - `RunHealth`：`ceiling`（这次判定用的上限）、`overall` / `test`（`HealthCounts`：全部用例、测试集）、
    `by_purpose`（用途 → `PurposeHealth`）、`routed_by`（实际做出路由的判断层 → 用例数）、`late_calls`、
    `valid`、`reasons`；
  - `HealthCounts`（用例数）：`cases`、`route_fallback`、`route_lost_votes`、`qa_judged`、`qa_unavailable`、
    `generation_attempted`、`generation_unusable`、`engine_errors`、`budget_cut`；
    `PurposeHealth`（调用数）：`calls`、`failed`、`timeouts`、`truncated`、`empty`、`unusable`、`errors`；
  - `allowed(n, ceiling)`：n ≤ 0 时是 0，否则 max(1, floor(ceiling × n))（至少容许 1 条）；
  - `assess(overall, test=None, *, ceiling=DEFAULT_CEILING, lost_vote_ceiling=LOST_VOTE_CEILING)` 返回不算数的原因
    （空列表 = 算数），全部用例看一遍，给了测试集再单独看一遍（句子前加"测试集："）：`route_fallback`、
    `engine_errors` 超过 `allowed(cases, ceiling)`，`qa_unavailable` 超过 `allowed(qa_judged, ceiling)`，
    `generation_unusable` 超过 `allowed(generation_attempted, ceiling)`，`route_lost_votes` 超过
    `allowed(cases, lost_vote_ceiling)`。`DEFAULT_CEILING` = 0.02，`LOST_VOTE_CEILING` = 0.10。时间预算截断
    （`budget_cut`）是 §12.1 的正常行为，照实展示，不算"模型没被评到"；
  - `error_label(detail)`：一次失败调用的 `llm.usage` detail → `PurposeHealth.errors` 的键。按顺序：kind 是
    timeout → `timeout`；有 status → `http_<状态码>`，有 code 再接 `:<code>`；有别的 kind → kind；都没有 →
    `error`（异常类型名），连它也没有 → `unknown`。
- `llm.usage` 审计 detail 的可选键（`rodit.llm.metering.MeteredLLMClient` 写，A 实现）：失败时 `kind`、`status`、
  `code`（知道才写）；成功时 `finish_reason`（不是 None 也不是 `stop` 才写）、`empty: true`（文本为空才写）。
  正常的成功调用 detail 和原来一样；detail 里照旧没有提示词和输出原文（§5.3）。
- 连通性检查 `rodit.eval.llm_env`：`preflight(client, config=None) -> list[str]`（config 是这次评测的配置；
  返回给人看的摘要，一行一条）、`PreflightFailed(RuntimeError)`（检查没过；消息是给操作的人看的完整说明，可以多行，
  不含密钥）、`via_proxy(client) -> bool | None`（请求是不是经环境里配置的代理发出去的；不知道、或注入了
  transport 时为 None；不返回代理地址）。现在 `preflight` 还是只发一个几个 token 的请求、返回空列表，
  `via_proxy` 一律是 None，C1 实现。
- 评测命令行 `rodit.eval.cli`：`EvalCliReport.health: RunHealth | None`（离线替身为 None，C2 填）；
  `--skip-preflight`（跳过连通性检查，只在调试时用）；`main` 调 `preflight(llm, config)`，返回的每一行在开跑前打到
  标准错误，`LLMError` 照旧包成"大模型连通性检查失败：…"，`PreflightFailed` 走原有的 RuntimeError 分支，退出码都是 2。
  退出码 3（这一轮没有有效评到模型）和 `--allow-degraded` / `--max-degraded` 由 C2 加。

## 5. 组装（rodit.app）

- `build_unit`：一个平台单元（§9.1）的全部组件，只接收已经造好的外部依赖，不读环境变量；
- `demo.build_demo_unit`：内存仓储 + 合成数据 + 模拟适配器（模式 B / C）+ 离线替身，单元里只有本平台的店铺；
- `production.build_production_unit`：PostgreSQL + 境内大模型（计量用量）；平台只读工具、适配器、
  售后写接口由平台云内的实现注入（沙箱调不通开放平台）；
- `AssistService`：应用流程。买家消息按会话串行（会话锁用完即释放，不会越积越多）；影子模式不展示；
  全自动只由引擎加 AI 标识、发送成功才记为已发送，发送失败或店铺加载失败一律转人工（§12.2）；
  客服发出的文字（反馈按钮或平台回声）写回会话，同一次发送的两份记录只留一份；
  撤回的消息从会话里去掉，按它给的推荐过期、侧边栏刷新（撤回先到时留标记）；
  取消订购和在途处理互斥（按店铺的读写闸门：先等在途消息处理完，再删除该店铺在本单元的全部数据，§8.4）。
- `rodit.api`：HTTP 接口（`create_app`）和模式 C 独立话术助手网页（`/assist`，原生 HTML / JS / CSS，
  只调已有接口，严格 CSP，令牌只放在请求头和 sessionStorage）；
- `rodit.ops`：部署一个平台单元的入口（`python -m rodit.ops serve | migrate | issue-token | local-init`）。
  生产模式没有注入平台实现时拒绝启动，除非明确只开模式 C（Phase 0）；`/healthz`、`/readyz`、`/metrics`
  挂在 `create_app` 之外（`install_ops`），指标从审计事件里采集，标签不含买家数据；
- `rodit.showcase`：客户演示站（`python -m rodit.showcase`，独立 FastAPI 应用，不挂进 `create_app`、不进
  `rodit.ops`）：每个平台一个演示单元（合成数据 + 离线替身），回放近 5 周历史，工作台、售后审核、看板、合规页；
- 售后审核工作台（`rodit.app.aftersale_desk`、`api/routes_aftersale.py`、网页 `/aftersale`）：队列只读，
  批量跑规则走 `AssistService.review_aftersale`，确认执行仍是原来的接口；
- 平台客服指标（`rodit.app.platform_metrics` + `rodit.feedback.platform_metrics`、`api/routes_platform_metrics.py`、
  `ops sync-platform-metrics`）：同步、商家登记、接入前后对比报表；写操作在 `processing(shop_id)` 里；
- `rodit.eval`：§13 评测。默认离线替身；`--llm env` 用真实大模型跑完整链路，报告 §12.1 各环节耗时、
  §14 用量和成本，`--baseline` 做 §13.5 回归比较，`--classifier` 用训练好的路由分类器；
  `rodit.eval.compare` 做判断层离线对比（§6.3、§6.4、§13.3，含 Jev 在合成数据上的表现）；
  `recalibrate`（§13.5 每月重算阈值）、`train`（§6.4 训练路由分类器）由 `rodit.ops` 的离线任务调用；
- `AssistService.console`（`rodit.app.console`）：商家控制台，知识编辑、店铺配置、商品同步（§9.1）；
  `AssistService.rollout`（`rodit.app.rollout`）：上线状态、影子 ↔ 智能辅助切换、每周人工复核（§13.4、
  §13.5）。写操作都在 `AssistService.processing(shop_id)` 里做，和取消订购互斥；
- 角色（`rodit.api.auth`）：agent 客服、manager 店长、merchant 商家、integration 平台对接、
  reviewer 复核人员（我们的质检人员，按店铺授权；看推荐原文留访问审计）。
