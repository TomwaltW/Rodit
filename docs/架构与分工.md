# 架构与分工

> 对应方案：`电商平台AI客服方案_v0.2.md`（下称「方案」）。本文件描述代码怎么组织、模块之间的契约，
> 以及并行开发时每个模块归谁。方案是"做什么"，这里是"代码里怎么落"。

## 1. 分层与依赖方向

```
rodit.core            契约层：枚举、数据模型、判断层格式（Jev）与 state 构造、端口协议、配置、
                      证据规则、共享词表、个人信息最小化、审计事件名、每种路由结果的执行计划
rodit.inmemory        core.ports 的内存实现：各仓储、缓存、离线向量（测试、本地演示、模式 C 单进程）
  ↑ 所有子包只依赖 core（+ inmemory）；子包之间不互相 import（组装在 rodit.app / 测试里做）
rodit.decision        判断层实现（§6.4）            rodit.knowledge   知识中心（§5.2）
rodit.routing         路由规则（§6.6）              rodit.tools       平台只读工具、物流（§7.1、§7.2）
rodit.generation      答案生成（§5.4）              rodit.aftersale   售后问答依据 + 审核助手（§7.3）
rodit.qa              答案质检（§5.5）              rodit.adapters    平台接入层（§8）
rodit.engine          编排：懂→找→写→判（§5）       rodit.feedback    反馈闭环与报表（§5.8、§12.4）
rodit.storage         PostgreSQL 仓储（§9.2、§10）   rodit.llm         大模型 HTTP 客户端（D5）
rodit.eval            评测与校准（§13）             rodit.api         HTTP 接口（模式 C、反馈、审核）
rodit.testing         合成数据、测试替身、仓储契约测试（contracts）；只用于测试和本地演示
```

例外：`rodit.routing` 可以依赖 `rodit.decision`（路由在判断层不可用时要退回规则实现）。
集成阶段新增的 `rodit.app`（组装）、`rodit.api`、`rodit.eval` 可以依赖所有子包。

## 2. 一条买家消息怎么走（§4.2、§11）

```
PlatformAdapter.peek_shop_id(raw) → 店铺（不改任何状态）      （app 层据此核对调用方身份和授权，§9.2、§8.4）
PlatformAdapter.on_event(raw) → StandardMessage | 回声 | 撤回  （adapters，平台差异止于此）
  → 客服 / 机器人发出的文字（回声）写进会话；撤回的消息从会话里去掉、按它给的推荐过期并刷新侧边栏，
    撤回先于消息到达时留标记，消息到了也不保存、不回答（app 层 + 会话仓储）
  → ConversationRepository.add_message（按 msg_id 去重）；晚到的旧消息只入库，重算最新一轮（§8.3）
  → 会话理解：合并连发、最近 5 轮、指代到商品 / SKU / 订单 → ConversationContext   （engine）
  → Router.route(ctx) → RouteDecision                        （routing + decision，§6.6 八条规则）
  → EvidenceRetriever.retrieve(ctx, route) → EvidenceBundle  （knowledge；工具证据经 ToolEvidenceProvider）
  → AnswerGenerator.generate(...) → [Draft]                  （generation：FAQ / 模板优先，其次大模型）
  → QualityGate.check(...) → QAResult                        （qa：硬规则 + 判断层质检，不过则带原因重写一次）
  → EngineResult（推荐卡片 / 提醒 / 转人工 / 缺失知识）       （engine）
  → PlatformAdapter.show_suggestions / send（仅全自动）       （app 层）
  → 客服操作 → FeedbackService（采纳、修改、弃用）             （feedback）
```

售后审核是另一条链路：`ToolGateway` 拉售后单 → 审核规则 R1–R8 → 状态机 → 客服确认 →
重读状态 → `AfterSaleActionPort`（幂等键）→ 审计。问答引擎永远不碰写接口。

## 3. 契约约定（所有模块都要遵守）

- **标准格式**：引擎只认 `core.models.StandardMessage`；判断层只认 `core.decision` 的 Jev 格式，
  state 只由 `core.states` 构造（内部已脱敏）。
- **配置分层**：`Shop.config_overrides` 只存店铺覆盖项；生效配置用 `core.config.effective_shop_config`
  算出，放在 `ConversationContext.config`，各步骤只读它（§9.3）。
- **执行计划**：每种路由结果跑哪些步骤见 `core.pipeline.ACTION_PLANS`；多问题（规则 5）按
  `RouteDecision.parts` 分条执行。
- **留痕分工**：decision_log 由 Router（route）和 QualityGate（qa）写；audit_log 的事件名见
  `core.audit.AuditAction`，引擎每条消息写一条 `engine.result` 汇总；推荐记录由引擎写入并负责过期。
- **证据 ID 与冲突**：只能用 `core.evidence` 的构造函数；各类证据 `data` 的结构、topic 冲突规则
  （被覆盖的证据从 evidences 移除、只记 id）见该模块文档字符串。平台规则是单独的证据来源（PLATFORM）。
- **问题定义**：路由和质检的问题在 `core.questions`，改文字会改版本号（写进 decision_log）。
- **个人信息**：任何进提示词、判断层请求、审计日志的买家文本都先过 `core.pii.mask_pii`；
  模型里没有昵称、手机号、地址字段；`buyer_ref` 由注入的 `core.pii.BuyerRefHasher` 生成（盐来自
  环境变量，测试用 `fixtures.TEST_SALT`）。
- **Jev**：判断层实现有 `accepts_buyer_data`；Router / QualityGate 构造时用
  `core.decision.require_buyer_data_ok` 拒绝不能处理买家数据的实现；配置里 provider 不能是 jev（§6.2）。
- **售后写操作**：写接口只接受 `HumanConfirmation`；幂等键用 `aftersale_idempotency_key`（平台状态版本）；
  状态机合法迁移见 `REVIEW_TRANSITIONS`，可操作状态见 `ACTIONABLE_STATUSES`。
- **店铺隔离**：所有仓储方法、缓存都按 `shop_id` 分开，实现不得跨店返回数据（§9.2）；
  仓储实现都要通过 `rodit.testing.contracts`（含串店测试 `check_cross_shop_isolation`）。
- **时间**：业务代码用注入的 `Clock`，不直接调 `datetime.now()`；所有时间带时区。
- **异常**：用 `core.errors` 的类型表达可降级的失败（`LLMError`、`DecisionError`、`ToolUnavailable`…），
  降级规则见方案 §12.2。
- **只读**：问答链路只用 `ToolGateway`；`AfterSaleActionPort` 只有售后审核助手能用，且必须有人确认。
- **测试**：单元测试不依赖网络；大模型用 `testing.fakes.FakeLLMClient`，平台用 `InMemoryToolGateway`，
  数据用 `testing.fixtures.build_demo_world()`（全部合成）。PostgreSQL 测试打 `@pytest.mark.pg`，
  连不上时自动跳过。

## 5. 组装（rodit.app）

- `build_unit`：一个平台单元（§9.1）的全部组件，只接收已经造好的外部依赖，不读环境变量；
- `demo.build_demo_unit`：内存仓储 + 合成数据 + 模拟适配器（模式 B / C）+ 离线替身，单元里只有本平台的店铺；
- `production.build_production_unit`：PostgreSQL + 境内大模型（计量用量）；平台只读工具、适配器、
  售后写接口由平台云内的实现注入（沙箱调不通开放平台）；
- `AssistService`：应用流程。买家消息按会话串行（会话锁用完即释放，不会越积越多）；影子模式不展示；
  全自动只由引擎加 AI 标识、发送成功才记为已发送，发送失败或店铺加载失败一律转人工（§12.2）；
  客服发出的文字（反馈按钮或平台回声）写回会话，同一次发送的两份记录只留一份；
  撤回的消息从会话里去掉，按它给的推荐过期、侧边栏刷新（撤回先到时留标记）；
  取消订购和在途处理互斥（按店铺的读写闸门：先等在途消息处理完，再删除该店铺在本单元的全部数据，§8.4）。
- `rodit.api`：HTTP 接口（`create_app`）和模式 C 独立话术助手网页（`/assist`，原生 HTML / JS / CSS，
  只调已有接口，严格 CSP，令牌只放在请求头和 sessionStorage）；
- `rodit.eval`：§13 评测。默认离线替身；`--llm env` 用真实大模型跑完整链路，报告 §12.1 各环节耗时、
  §14 用量和成本，`--baseline` 做 §13.5 回归比较。

## 6. 方案待决策项的默认实现（§3）

| 项 | 代码里的默认 |
|---|---|
| D1 首发平台 | 核心与平台无关；三个平台都有模拟适配器 |
